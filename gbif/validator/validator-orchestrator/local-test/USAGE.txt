# Local integration harness (Podman Compose)

Run from `gbif/validator/validator-orchestrator`.

## 1. Build the orchestrator image

Build the executable shaded JAR first. Verify there is exactly one `target/*-shaded.jar`.

```sh
podman build \
  --build-arg BASE_REGISTRY=docker.gbif.org/third-party \
  --build-arg JAR_FILE="target/$(basename "$(echo target/*-shaded.jar)")" \
  -f docker/Dockerfile \
  -t localhost/validator-orchestrator:test .
```

## 2. Run with the real analyser

The default analyser image is `docker.gbif.org/dwc-dp-analyser-service:0.0.6`.
Podman uses fully qualified image references for both services.

Prepare a real DWc-DP archive repository and a writable analyser work directory.
The analyser looks up archives by the UUID supplied in the request. Ensure the archive
is present in the layout expected by `dwc-dp-analyser-service` under the repository.
Use an **absolute path** for these bind mounts.

```sh
mkdir -p ./local-test/workdir
DATAPACKAGES_DIR=/absolute/path/to/datapackages \
DWCDP_WORKDIR="$(pwd)/local-test/workdir" \
podman compose -f local-test/compose.yaml --profile analyser up -d
```

Run the same environment variables for subsequent `podman compose` commands if your
Compose provider recreates containers; otherwise simply use `logs`:

```sh
podman compose -f local-test/compose.yaml logs -f analyser orchestrator mock-validator-ws
```

The analyser is configured with:

- Broker `rabbitmq:5672`, credentials `localtest/localtest`, vhost `/`.
- Input queue `validator_dwcdp_analysis`, bound by `trigger.py` to the `occurrence`
  topic exchange with routing key `validator.dwcdp.analysis`.
- Completion exchange `occurrence`, routing key `validator.dwcdp.analysis.finished`.
- Registry URL, user, and password empty to disable its Registry integration.
- Mounted input `/data/datapackages` and writable `/data/workdir`.

The orchestrator's completion listener expects the real `DwcDpValidationFinished`
payload: `datasetUuid`, `attempt`, `valid`, and `validationReport`. The completion
processor uploads `validationReport` to the mock validator-ws and records the step
outcome. `valid: false` is treated as an invalid-data completion, not as a successful
validation. The actual analysis requires an accessible and valid DWc-DP archive.

## 3. Trigger validation

Choose the UUID corresponding to the archive in `/data/datapackages`:

```sh
python3 local-test/trigger.py --uuid YOUR_ARCHIVE_UUID
```

The script seeds the mock validator-ws, declares the analyser request queue and
binding, and publishes the initial orchestrator event. It does not create or copy
input data into the archive repository.

```sh
curl http://127.0.0.1:18080/validation/YOUR_ARCHIVE_UUID
podman compose -f local-test/compose.yaml logs -f mock-validator-ws
```

The mock logs WS GET/PUT updates and validation report uploads. RabbitMQ management:
http://127.0.0.1:15672 (`localtest` / `localtest`).

## Mock completion without the analyser

Start only the infrastructure and orchestrator:

```sh
podman compose -f local-test/compose.yaml up -d
python3 local-test/trigger.py
python3 local-test/trigger.py --complete UUID_PRINTED_ABOVE
```

Do **not** publish `--complete` for a UUID concurrently being processed by the real
analyser: it would create a duplicate/computationally inconsistent completion.

## Limitations

This local harness deliberately enables the **unsafe** orchestrator consumers. Use
one orchestrator instance only. WS updates and RabbitMQ dispatch are not atomic.
The mock implements only validation GET/PUT and validation-report PUT, not the full
validator-ws API. No automatic retry or remaining-pipeline handoff is provided.

Stop with `podman compose -f local-test/compose.yaml --profile analyser down`.
